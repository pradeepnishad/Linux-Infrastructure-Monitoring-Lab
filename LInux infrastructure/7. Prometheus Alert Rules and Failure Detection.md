# Prometheus Alert Rules and Failure Detection

## 1. Overview

Prometheus alert rules evaluate metric expressions and change alert state when configured conditions are met.

The project used alert rules to detect server unavailability and monitor CPU, memory, and disk conditions.

## 2. Rule Configuration

The rules file used in the lab was:

```text
/etc/prometheus/rules/linux-alerts.yml
```

The Prometheus interface displayed the rule group:

```text
linux-server-alerts
```

Verify the actual path and group name on the final system.

## 3. Configured Rules

| Alert rule | Intended purpose |
|---|---|
| `InstanceDown` | Detect a monitored target that remains unavailable |
| `HighCPUUsage` | Detect high CPU utilization |
| `DiskSpaceLow` | Detect low free disk space or high disk utilization, depending on its expression |
| `HighMemoryUsage` | Detect high memory utilization |

The exact thresholds for CPU, memory, and disk must be taken from the final `linux-alerts.yml` file. They should not be inferred from the alert names.

## 4. InstanceDown Rule

The expression displayed in the Prometheus interface was:

```promql
up{job="linux-servers"} == 0
```

The configured duration was:

```yaml
for: 1m
```

This means the condition must remain true for one minute before the alert enters the firing state.

The alert checks whether Prometheus can successfully scrape the target. It does not necessarily prove that the entire VM has powered off; the exporter, network, firewall, or scrape path may also be responsible.

## 5. Alert States

### Inactive

The alert expression is not currently triggering the alert.

### Pending

The expression is true, but the configured `for` duration has not yet elapsed.

### Firing

The condition has remained true for the required duration.

## 6. Testing an Alert

During the project, an `InstanceDown` alert was observed firing for:

```text
10.10.10.12:9100
```

The Node Exporter service was subsequently restarted and returned to `active`. Prometheus then showed all three `linux-servers` targets returning `1` in the availability query.

This demonstrates an observed failure and recovery scenario. For a repeatable test, record the target state and alert state before, during, and after the test.

## 7. Validate the Rules

```bash
sudo promtool check rules /etc/prometheus/rules/linux-alerts.yml
```

Also validate the main configuration:

```bash
sudo promtool check config /etc/prometheus/prometheus.yml
```

A duplicate `rule_files` field caused a configuration validation error during troubleshooting. Validate both the main configuration and the rule file after making changes.

## 9. Troubleshooting Alerts

If an alert is not firing:

1. Check the expression in Prometheus.
2. Query the underlying metric directly.
3. Check the target's status on `/targets`.
4. Review the alert's pending duration.
5. Validate the rules file with `promtool`.
6. Check Prometheus logs if rule evaluation is failing.
