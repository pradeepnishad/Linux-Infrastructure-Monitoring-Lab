# PostgreSQL Backup and Recovery Validation

## 1. Overview

This component documents a PostgreSQL backup recovery exercise.

The goal was to inspect a custom-format database dump, verify that copied files matched using SHA-256 checksums, restore the dump into a separate test database, and query the restored data.

## 2. Backup Information

The captured archive was named similarly to:

```text
infra_monitor_2026-10-21_22-21-25.dump
```

The archive metadata showed:

| Property | Observed value |
|---|---|
| Source database | `infra_monitor` |
| Archive format | `CUSTOM` |
| Compression | `gzip` |
| Dump version displayed | `18.6` |
| Table of interest | `public.server_inventory` |

Confirm the actual filename, path, and PostgreSQL version before reusing these details.

## 3. Inspect the Backup Archive

PostgreSQL's `pg_restore --list` command displays the contents of a supported archive without restoring it.

```bash
sudo -u postgres pg_restore --list \
  /var/backups/postgresql/infra_monitor_2026-10-21_22-21-25.dump \
  | head -20
```

This helps determine whether the archive can be read and what database objects it contains.

It does not by itself prove that a complete restore will succeed.

## 4. Verify File Integrity

The `sha256sum` utility computes a SHA-256 hash for a file.

```bash
sha256sum /path/to/infra_monitor_2026-10-21_22-21-25.dump
```

The checksum observed on two machines matched:

```text
3413130cc6829dbc964a01a86813f9d955177980417f493bf39db9230cf46f55
```

Matching SHA-256 hashes provide strong evidence that the copied files contain the same bytes.

A matching hash does not independently prove that the backup contains all expected database data or can be restored successfully.

## 5. Restore Validation

The backup was restored to a separate test database named:

```text
infra_monitor_offsite_test
```

The restored table was checked using:

```bash
sudo -u postgres psql -d infra_monitor_offsite_test -c \
  'SELECT COUNT(*) AS inventory_rows FROM server_inventory;'
```

Observed result:

```text
 inventory_rows
----------------
              3
(1 row)
```

This confirms that the `server_inventory` table contained three rows in the test database at the time of the check.

## 6. Why Restore to a Test Database?

Restoring to a separate database helps avoid overwriting the source database during testing.

A restore test provides stronger evidence than merely checking that a backup file exists.

## 7. What This Test Proves

The exercise demonstrated that:

- The archive could be inspected.
- Two copies had matching SHA-256 hashes.
- The test database contained the expected table.
- A query against the restored table returned three rows.

## 8. What This Test Does Not Prove

A complete database recovery test should also verify the expected tables, sequences, indexes, constraints, permissions, roles, and application-level behaviour.

The row-count check alone does not establish that every database object was restored correctly.

## 9. Recommended Recovery Procedure

For future backups:

1. Create the backup using the intended PostgreSQL backup procedure.
2. Record the source database, timestamp, file size, and tool version.
3. Compute and record a checksum.
4. Copy the backup to the intended destination.
5. Verify the checksum at the destination.
6. Inspect the archive.
7. Restore to an isolated test database.
8. Verify expected database objects and records.
9. Document the recovery result and any errors.

## 10. Security Notes

- Do not commit database dumps to a public Git repository.
- Restrict access to backups.
- Do not publish database credentials.
- Keep the source backup unchanged during recovery testing.
- Store backups in a location separate from the data they protect.

## 11. Learning Outcomes

This exercise provided hands-on experience with PostgreSQL archive inspection, file integrity verification, test database restoration, SQL validation, and recovery documentation.
